# 规则：AI 助手代码注释规范

**本文件即时生效**（2026-09-09 起）。适用于所有新增/修改的代码（Kotlin / C++ / 脚本一律适用）。与 `rules/code-quality.md` 的关系：code-quality 1.2 已有"注释撒谎 / 无效注释"坏味道条目，本文件承载**注释内容的完整规范**（最终状态优先 / 历史表述禁令 / 一致性检查清单），两者交叉引用不重复。

---

## 1. 核心原则

项目中的代码注释必须以**当前最终状态**为准。

注释的职责是帮助后续开发者和 AI 理解：

- 当前代码是什么
- 当前代码负责什么
- 为什么当前必须这样实现
- 当前存在什么约束
- 哪些地方不能随意修改

注释不是开发日志，不是修改记录，也不是历史档案。后续维护人员阅读代码时，应当能够只根据当前代码和当前注释，准确理解项目现在的状态，而不会被过去已经废弃的实现干扰。

---

## 2. 禁止在代码注释中记录修改过程

除非历史信息对理解当前代码具有不可替代的价值，否则禁止以下六类注释。

### 2.1 禁止记录"之前是什么"

```kotlin
// ❌ 禁止
// 之前使用 OpenGL ES
// 原来这里是 CPU 渲染
// 之前这个函数叫 XXX
// 原来使用旧的数据结构

// ✅ 应直接描述当前状态
// 使用 Vulkan 进行 GPU 渲染。
```

### 2.2 禁止记录"删除了什么"

```kotlin
// ❌ 禁止
// 删除旧的 CPU 渲染逻辑
// 删除了之前的缓存系统
// 移除不再使用的 XXX
```

删除后当前代码已不存在该功能，通常无需留下任何注释。

### 2.3 禁止记录"新增了什么"

```kotlin
// ❌ 禁止
// 新增 Vulkan 支持
// 新增异步加载

// ✅ 应写成
// 使用异步任务加载地图资源，避免阻塞渲染线程。
```

例外：这个"新增功能"本身就是当前代码需要解释的功能时，按当前功能描述，不按"新增"描述。

### 2.4 禁止记录"从什么迁移到什么"

```kotlin
// ❌ 禁止
// 从 Kotlin 迁移到 C++
// 从 OpenGL ES 迁移到 Vulkan

// ✅ 当前项目已确定使用 C++ 和 Vulkan，就直接描述当前架构
// Android 图形渲染后端，当前使用 Vulkan。
```

### 2.5 禁止记录"为了修复某问题而修改"

```kotlin
// ❌ 禁止
// 修复之前手机黑屏的问题
// 修复内存泄漏

// ✅ 应描述当前仍然有效的技术约束
// 在资源上传完成后才允许提交对应的绘制命令，
// 避免使用尚未完成 GPU 上传的纹理。
```

### 2.6 禁止留下已失效的 TODO

```kotlin
// ❌ 禁止（已经改成 Vulkan 还留着）
// TODO：以后改成 Vulkan

// ❌ 禁止（问题已解决还留着）
// TODO：优化地图加载
```

已解决的 TODO 一律删除。

---

## 3. 注释必须描述"最终事实"

修改代码后，必须重新检查相关注释。原注释描述旧状态的，同步改为当前状态：

```kotlin
// ❌ 原注释（代码已改为 GPU 绘制后失效）
// 使用 CPU 绘制地图

// ✅ 同步为
// 使用 GPU 绘制地图

// ❌ 禁止写成历史对照
// 原来使用 CPU 绘制地图，现在改为 GPU
```

**代码与注释冲突时，代码的当前实际行为优先，注释必须改为与代码一致。** 禁止为了让代码"符合旧注释"而恢复已废弃的设计。

---

## 4. 历史信息保留条件：保留"原因"，删除"故事"

仅当历史原因对当前设计不可替代时保留，且必须转换为**当前仍然有效的设计规则**：

```kotlin
// ❌ 修改故事
// 之前某手机出现崩溃，所以后来改成这样。

// ✅ 当前仍然有效的技术原因
// 必须保持 16 字节对齐，以满足部分移动端 GPU 的数据对齐要求。
```

---

## 5. 禁止把代码注释写成开发日志

```kotlin
// ❌ 全部禁止
// 2026/09/08 修改
// 后来发现有问题，再次调整
// 第一次方案...第二版方案...最终采用第三版
// 经过多次尝试后...
```

这些内容属于 Git commit、CHANGELOG、技术文档——三者不得混入源代码注释（见第 10 节信息分层）。

---

## 6. 禁止描述当前代码中不存在的东西

- 类/系统已不存在 → "以前的旧地图系统会..." 一律删除
- 功能已删除 → "这里以前负责 XXX" 一律删除
- 接口已废弃 → "以前调用 XXX" 一律删除（除非当前代码确实需要该历史背景）

**注释必须尽量与当前代码形成一一对应关系。**

---

## 7. 不为了"看起来详细"而增加信息

```kotlin
// ❌ 历史堆砌
// 这里以前使用旧的地图加载方式。
// 后来为了性能改成异步加载。
// 中间曾经尝试过线程池。
// 最终删除了旧实现。

// ✅ 一句话当前状态
// 异步加载地图资源，避免阻塞主线程。
```

当前实现已足够直观时，甚至可以不写注释。

---

## 8. 优先解释"为什么"，而不是"做了什么"

代码本身已能表达 `cache.clear()`，无需写 `// 清空缓存`。但存在特殊原因时必须写：

```kotlin
// 切换场景前必须清空临时缓存，避免旧场景资源被错误复用。
cache.clear()
```

原则：**代码解释"做什么"，注释主要解释"为什么"。**

---

## 9. 优先记录稳定的设计规则

| 类别 | 示例 |
|------|------|
| 生命周期规则 | `Renderer` 必须在所有 GPU 资源销毁前保持有效 |
| 线程规则 | GPU 资源创建必须在渲染线程执行 |
| 数据约束 | `worldSize` 必须使用世界坐标，不得传入屏幕坐标 |
| 性能约束 | 此路径位于每帧更新循环中，禁止在此执行动态内存分配 |
| 平台约束 | Android Vulkan 资源上传必须通过指定的 staging 路径完成 |
| 架构约束 | 地图逻辑层不得直接访问 Vulkan 对象 |

---

## 10. 信息三层分离

| 层次 | 记录内容 | 示例 |
|------|---------|------|
| A. 源代码注释 | 当前状态 + 当前设计 + 当前约束 + 必要原因 | — |
| B. Git 提交记录 | 这一次修改了什么 | Replace CPU map rendering with Vulkan rendering |
| C. 技术文档 / CHANGELOG | 项目为什么发生重大变化、架构如何演进 | 地图渲染系统从旧实现迁移至 Vulkan |

---

## 11. 注释一致性检查（每次改码后必做）🔴

每次 AI 修改代码、重构代码、删除功能、替换实现之后，必须对受影响注释逐项过以下检查：

| # | 检查项 | 处置 |
|---|--------|------|
| 1 | 注释是否仍然描述当前代码？ | 不是 → 修改或删除 |
| 2 | 是否留下旧实现的描述且对当前代码没有必要？ | 删除 |
| 3 | 是否出现"之前 / 原来后来 / 现在改成 / 新增 / 删除 / 迁移"等历史性表述？ | 无必要 → 删除并改写为最终状态 |
| 4 | 是否出现已不存在的类、函数、系统、变量或架构？ | 删除 |
| 5 | 是否出现已解决的 TODO？ | 删除 |
| 6 | 是否把开发过程写进了代码？ | 删除 |
| 7 | 是否存在误导未来 AI 的信息（可能让不了解历史的人误以为旧系统仍存在）？ | 立即修改 |

---

## 12. 禁止 AI 工作汇报式注释 🔴

AI 不得为了体现"自己做了哪些工作"在代码中加入：

```kotlin
// ❌ 全部禁止
// AI修改
// 本次优化
// 根据需求新增
// 按照用户要求修改
// 修复完成
// 重构完成
```

任何以"向后续人员汇报本次 AI 工作"为目的的注释都不得出现在源代码中。汇报内容写在任务完成报告里。

---

## 13. 最终执行规则

- 只让源代码注释描述项目的**最终状态**
- 不在注释中记录已经发生的修改过程
- 不记录删除了什么、新增了什么、之前是什么
- 不把 AI 的工作过程写进代码
- 不保留已失效的 TODO、旧架构描述或废弃功能说明
- 历史原因仍影响当前实现时，只保留当前仍然有效的技术原因，不记录完整修改故事
- 每次修改代码后，必须同步检查并清理受影响的旧注释

**最终目标**：任何一个从未参与过项目开发的新 AI 或新开发者，仅阅读当前代码和当前注释，就应该得到对项目当前状态的正确认识，不因历史注释产生误判。
