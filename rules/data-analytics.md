# 规则：数据埋点与留存运营规范

> ⚠️ **预留规范（未实现，约束未来设计）**：本文约束未来数据埋点体系。现状基线：无事件埋点、无留存漏斗、无 A/B 测试（TapTap SDK 仅有登录/合规/分析自带上报）。见 `docs/knowledge-base.md#扩展性现状盘点`。

## 1. 埋点原则（🔴）

### 1.1 关键漏斗事件强制埋点（FTUE 漏斗）

对应行业留存基准（D1 中位数 22%、超 50% 用户首日流失），以下事件**必须**埋点：

| 漏斗阶段 | 事件 | 用途 |
|---------|------|------|
| 安装/首启 | `app_first_launch` | 渠道归因 |
| 新档创建 | `game_new_save` | 首日转化 |
| 首次战斗 | `battle_first_win` | FTUE 完成度 |
| 首次突破 | `breakthrough_first` | Aha Moment 验证 |
| 首日回访 | `session_d1_return` | D1 留存 |
| D7/D30 回访 | `session_d7_return` / `session_d30_return` | 周/月留存 |

行业数据支撑：完成引导 + 首战 + 首次成长反馈的用户 D7 留存 41.2%（未完成用户 3.6 倍）；教程 >10 分钟强制引导流失 35%。

### 1.2 事件规范

- **snake_case 事件名** + **属性白名单**（事件属性必须是预注册键，禁止自由键）
- **禁止埋点 PII**：昵称/设备号明文/真实身份一律禁止；用户标识去标识化（ID 哈希）
- **事件字典维护**：事件名 + 属性定义登记到 `docs/knowledge-base.md`（事件字典章节），新增事件必须登记

### 1.3 非阻塞（🔴 性能）

- **禁止在主线程/游戏循环热路径执行埋点**（游戏循环 100ms tick、每旬热路径列直读——CLAUDE.md 10.x 性能规范）
- 批量异步上报（攒批 + 后台线程），单次上报不阻塞游戏逻辑
- 埋点失败静默降级（不影响玩家体验），禁止埋点抛异常进游戏主链路

## 2. 离线上报（🟡）

- 无网络时本地队列 + 网络恢复后批量补报
- 队列有上限（防膨胀：上限外的旧事件丢弃，日志记录丢弃量）

## 3. 留存监控（🟡）

- **D1/D7/D30 对比行业中位数建立项目基线**（2024-2026 行业基准：D1 中位数 ~22%、D7 ~4%、D30 <1%；"35/15/5"新基准）
- 自定义留存：按玩法参与度分组（参与秘境 vs 未参与、签到达标 vs 未达标），定位流失断点
- 漏斗分析：从埋点事件还原漏斗（首启 → 新档 → 首战 → D1 回访），定位流失环节

## 4. A/B 测试（🟡）

- 由 RemoteConfig 配置驱动（rules/commercialization.md RemoteConfig 规范：本地默认值兜底 + Key 命名 + 版本化）
- 分层实验：玩家分组（按 UID 哈希分桶）+ 版本隔离（同组玩家同版本同实验）
- 实验指标：以留存/漏斗转化率为核心指标，不以短期收入为准（长期主义——CoC 四大原则）

## 5. 隐私合规（🔴）

- 埋点最小化：只埋运营决策需要的数据
- 去标识化：用户 ID 哈希处理，事件数据与真实身份隔离
- **隐私政策双入口同步**：游戏内 `PrivacyConsentScreen.kt` + 网站版 `docs/index.html`（CLAUDE.md 设计方案原则 5）
- 上线埋点前完成隐私政策评估（收集类型/目的/方式变更必须更新隐私政策）
- 第三方分析 SDK 接入同样触发隐私政策更新（商业化规范第 6 条同规则）
