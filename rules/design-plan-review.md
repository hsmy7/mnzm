# 方案自检清单（Design Plan Review Checklist）

> 对标代码审查清单（CLAUDE.md 13.3）的方案级检查表。**任何设计方案（新功能/重构/技术选型）在提交用户确认前，必须逐项过一遍本清单**——遗漏项在方案文档"影响范围清单"中显式声明理由。
> 更新日期：2026-09-09（新增第七节"盲区自查与完善建议"；2026-08-13 Godot 对标重构经验沉淀）。

---

## 一、未来场景推演（防"只看眼前"）🔴 必做

方案必须包含 **"未来场景推演"小节**，至少覆盖 6 个月档（1 年/3 年档按方案规模选做）：

| 推演维度 | 必答问题 | 反例（历史教训） |
|---------|---------|----------------|
| 规模增长 | 同类内容 ×10 时，本方案成本是否仍然线性可控？（新增 1 个 vs 新增 10 个） | UID 排序分配：新增资源使既有 UID 漂移（2026-08-13 修复为持久映射追加式） |
| 生命周期 | 本方案产出的东西在"构建/重启/重建/清缓存"全生命周期内行为一致吗？ | codegen 的 generatedAt 时间戳进 hash → 增量跳过永久失效（2026-08-13 修复） |
| 平台扩张 | 未来 iOS 端时本方案是否需要重做？（对照 platform-abilities.md 接口缺口清单） | AudioEngine 破坏 core/engine 零 Android 依赖自我声明（audio-thread-audit A1） |
| 运营演进 | 6 个月内数值/配置/活动调整时，本方案是否需要发版？（对照 RemoteConfig 绑定状态） | 数值硬编码 → 每次平衡调整等发版审核 |
| 兼容回退 | 本方案上线后若发现缺陷，能否关闭开关/回退，还是必须再发版？ | 无开关的深度重构 = 一次性赌注 |

## 二、技术债显性化（防"只修眼前、债留身后"）🔴 必做

方案必须包含 **"技术债与偿还计划"小节**，三列表：

| 债项 | 产生原因（为何现在不全做） | 偿还时机（明确触发条件） |
|------|--------------------------|------------------------|
| 例：命令通道零消费者 | 计划批准但无生产消费场景 | 出现纹理流送/动态图集时实现，或下次清理移除 |

**规则：**
- "后续优化"、"视情况而定"不是偿还时机——必须有可判断的触发条件
- 方案完成后，债项同步登记到 `docs/architecture.md` 待办登记表（D 系列）或 `docs/platform-abilities.md` 缺口清单（G 系列）
- 借债默认不允许；确需借债的必须有上述表格

## 三、YAGNI 反向检查（防"为未来臆造"）🔴 必做

- 方案中每个新抽象/新接口/新类型，**必须至少有一个当前生产消费者**（测试不是消费者）
- 无当前消费者的 → 从方案中移除，改登记为二、技术债条目
- 反例：FrameDrawCommand 三命令类（53 行死代码，2026-08-13 删除）；命令 FIFO 通道（实现后对抗审查删除，教训：**计划批准 ≠ 免于 YAGNI 审查**）

## 四、测试成本核算（防"测试拖垮 CI"）🔴 必做

| 检查项 | 必答问题 |
|--------|---------|
| 墙钟成本 | 每个新测试的**真实墙钟时间**是多少？（runTest 虚拟时间 ≠ 墙钟；迭代数 × 单次成本要估算） |
| 上限约束 | 单测试 > 30 秒墙钟吗？（是 → 拆小或降迭代；全量测试预算 ~10 分钟内） |
| 确定性偏差 | 守卫类测试的迭代数是否必要？（确定性偏差是系统性差异，单次迭代即可捕获——100 与 1000 守卫强度相同，见 HeavenlyTrialAnimationGuardTest 修正） |
| 环境依赖 | 测试依赖本机路径/文件存在/构建产物吗？（生成物依赖必须挂 Gradle 任务依赖，见 codegen 守卫测试接线） |

## 五、全局影响交叉核对（防"只见自己模块"）🟡 必做

- 逐项列出本方案触碰的 `rules/*.md` 规范文件（如 economy-design / commercialization / expansion-playbook）并确认无冲突
- 涉及货币/奖励 → 对照 `docs/knowledge-base.md` 经济基线表（源与汇闭环）
- 涉及平台能力 → 对照 `docs/platform-abilities.md`（接口缺口清单 G 系列）
- 涉及存档/Entity → 对照 `rules/database-migration.md`（先读规则再动 Entity）
- 涉及渲染特性 → 对照 `android/docs/renderer-feature-checklist.md`（双端一致性）

## 六、决策分级（防"该小修时大改、该大改时小修"）🟡 必做

方案开头必须声明本方案属于哪一级：

| 级别 | 判定 | 要求 |
|------|------|------|
| **眼前修复**（外科手术式） | 缺陷清晰、根因单一、无扩展需求 | 只改必须改的；引用 Karpathy 准则 3 |
| **架构级重构** | 同模式问题 ≥3 处 / 触及未来 6 个月规划 / 影响跨平台路径 | 按设计方案规则全流程（完整方案文档 + 对抗性审查；行业对标为 🟡 建议项，非强制前置） |
| **中间地带** | 拿不准时 | 按架构级出方案，但明确标注"最小切入路径"备选 |

## 七、盲区自查与完善建议（防"当局者迷"）🔴 必做

方案必须以 **"盲区自查与完善建议"** 作为**最后一个章节**：作者切换到审查者/对抗者立场，系统回答"本方案没有考虑到什么、遗漏了什么"，并逐条给出完善建议。

自查维度（逐项过一遍，禁止只挑容易的回答）：

| 维度 | 必答问题 |
|------|---------|
| 需求理解 | 需求是否存在第二种合理解读？字面需求与用户真实意图是否有偏差？ |
| 边界与极端 | 空值/极值/并发/中断/时序错乱下，本方案是否有定义的行为？ |
| 系统耦合 | 与既有机制的交互（结算层级/EventBus/存档/引导/配置开关/RNG 分区）是否全部枚举？ |
| 假设有效性 | 方案依赖的前提假设逐条列出：如何验证？不成立时的备选路径？ |
| 数据与兼容 | 旧存档/旧配置/中断后的半完成状态下行为是否明确？回滚路径是否存在？ |
| 非功能属性 | 性能/内存/功耗/安全/隐私合规是被评估过，还是默认"不适用"？ |
| 生命周期 | 运营调整、规模增长、iOS 移植时方案是否仍然成立（对照第一节逐项复核）？ |
| 流程盲区 | 测试覆盖不到的部分、监控盲区、发布/回滚流程的薄弱环节？ |

条目三要素：**盲点描述 + 潜在影响 + 完善建议**（建议必须可执行，禁止"加强关注"式空话）。

处置规则：
- 完善建议若实质影响方案主体（补充影响点/新增兼容措施/改变选型），**必须回写方案正文对应章节**，本章节只保留条目索引——禁止把已知缺陷留在附录不处理
- 有价值但暂不采纳的建议须说明理由；构成技术债的同步登记到第二节债表
- 确无实质性盲区时，禁止一句"无遗漏"敷衍——须逐维度给出自查结论与依据

## 八、方案完成度自检（提交用户前逐项勾选）

- [ ] 未来场景推演小节已写（≥6 个月档）
- [ ] 技术债与偿还计划小节已写（无债也需声明"本方案无新增债"）
- [ ] 盲区自查与完善建议小节已写（方案末章，逐条含"盲点+影响+建议"三要素，实质性问题已回写正文）
- [ ] 每个新抽象有当前生产消费者（或已移入债表）
- [ ] 新测试墙钟成本已核算
- [ ] rules/ 交叉核对完成（列出触碰的规范文件）
- [ ] 决策分级已声明
- [ ] 影响范围清单含经济/iOS 标签项（CLAUDE.md 设计方案规则第 3 条）
