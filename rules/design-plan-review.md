## 零、设计方案基本原则（编写规范）🔴

> 本节是方案评审的核心标准。**任何设计方案（新功能 / 重构 / 技术选型）动笔前先读本节；
> 提交用户确认前，再过一遍下文第一~八节的自检清单。**

**原则 1｜方案符合编写规范** — 方案必须使用统一结构编写，包含：
**背景与目标**（需求要点 + 成功标准）、**技术方案**（架构变化 + 关键类/接口 + 数据流）、
**影响范围清单**（格式见原则 3）、**兼容性分析**（Migration / 序列化 / 存档）、
**测试方案**（单元测试 + 对抗性审查要点）、**风险评估与兜底**、
**未来场景推演**（≥6 个月档，见第一节）、**技术债与偿还计划**（见第二节）、
**盲区自查与完善建议**（方案最后一个章节，见第七节）。
禁止用非结构化段落替代规范方案文档；方案文档必须独立可读，不依赖口头补充。

**原则 2｜功能模块化设计** — 新增功能必须设计为可独立发布、可单独测试、可通过配置开关控制启停的模块；
模块之间通过接口通信，内部实现变更不影响外部调用方。禁止把新功能硬编码嵌入既有类或函数形成面条式代码。
新增前必须检查能否通过扩展已有模块（`:core:engine/domain/` 或 `:core:engine/system/`）实现，避免重复造轮。

**原则 3｜全局视角** — 方案必须覆盖变更波及的所有子系统：UI（跨屏适配 + 输入法避让 + 对话框栈）、
存储（Migration + 向前兼容 + 向后兼容）、渲染（Vulkan + Canvas 双路径验证）、
测试（单元测试 + 集成测试 + 对抗性审查）、后续平台扩展（iOS 接入点预留）。
方案中必须包含**「影响范围清单」**，格式为 `文件路径 — 变更类型 — 变更说明`；遗漏视为方案不完整。
同时需检查变更是否与进行中或规划中的其他功能存在冲突，必要时协调优先级。

影响范围清单追加两个检查项：
- **经济影响**（`经济` 标签）— 涉及货币/奖励发放的方案必须列"源与汇"分析（产出源 + 消耗汇闭环，见 `rules/economy-design.md`）
- **iOS 影响**（`iOS` 标签）— 涉及平台能力（时间/存储/网络/加密/通知/支付/广告/分享）的方案必须列 Android/iOS 对等实现分析（见 `rules/code-quality.md` 跨平台章节）

**原则 4｜低高端设备兼容设计** — 所有涉及渲染、UI 框架、原生库加载的功能变更，必须预先评估在低端/老旧设备上的兼容性：

- **渲染管线双路径** — 任何渲染特性变更必须同时验证 Vulkan 和 Canvas（软件渲染）两套路径，确保低端 GPU（Mali-G5x/6x、PowerVR、Adreno 6xx 等）在 Vulkan 驱动缺陷下可用软件渲染降级
- **系统 HWUI 层同步降级** — 关闭 Vulkan 渲染决策必须同步关闭 Activity 级硬件加速（`android:hardwareAccelerated="false"`），因为定制 ROM（Magic UI、澎湃OS、OriginOS 等）可能在 Android < 15 上回传 SkiaVK/Vulkan HWUI，仅关闭游戏渲染层不够
- **所有 Activity 入口统一检查** — `MainActivity` 和 `GameActivity` 等所有 Activity 的 `onCreate()` 必须在 `super.onCreate()` 前检查 `VulkanPolicy.isAccelerationDisabled()` 并切换主题。仅保护一个 Activity 会导致启动阶段崩溃
- **API 级别守卫** — 所有 `Build.SOC_MANUFACTURER`（API 31+）、`Build.SOC_MODEL`（API 31+）等新增 API 字段必须在访问前用 `Build.VERSION.SDK_INT >= 31` 守卫，禁止在 `Application.onCreate()` 等启动阶段无保护访问，否则低 API 设备触发 `NoSuchFieldError` 直接闪退
- **GPU 黑名单对齐行业标准** — 参考 Unity Vulkan Device Filtering（Mali GPU Vulkan API < 1.0.61 自动降级）、Flutter Impeller（自动检测 MTK SoC 回退 OpenGL ES）、Chromium（Mali-G57 全面禁用 Vulkan）等行业标杆，持续更新已知问题 GPU/SoC 列表。新增黑名单条目需附带 Bugly 崩溃数据或行业报告引用
- **iOS 侧对等要求** — 渲染特性变更必须给出 iOS 侧对等实现方案（Metal 或软件渲染等价路径，参照 `SoftwareCanvasBackend`）；iOS 无 Vulkan/HWUI 问题，但需评估 Metal 驱动兼容性与 A8 及以下老机型。跨平台可移植性约束详见 `rules/code-quality.md` 第 1.5 节

设备分级、降级链与崩溃防御的完整设计见 `android/docs/vulkan-crash-defense-design.md`、
`android/docs/render-thread-crash-strategy.md` 与 `docs/adr/render-strategy-decision.md`。

**原则 5｜隐私合规与隐私政策同步更新** — 方案涉及以下变更时，必须同步评估并更新隐私政策：
新增或变更第三方 SDK（含 SDK 版本升级、初始化时机变化、数据收集范围变化）、
新增或变更个人信息收集的类型 / 目的 / 方式、新增或变更权限申请（Android 权限或 iOS 隐私权限）、
新增网络请求或变更数据传输方式（新增服务器端点、新增请求头信息等）、新增或变更数据共享第三方、
新增或变更广告 / 分析 / 推送模块。

隐私政策更新必须覆盖两个入口：
1. **游戏内隐私政策**（`PrivacyConsentScreen.kt`）— 更新展示内容或三方 SDK 链接
2. **网站版隐私政策**（`docs/index.html`，发布在 `https://hsmy7.github.io/mnzm/`）— 更新网页内容

变更说明需记录在方案文档的「影响范围清单」中，标注 `隐私合规` 标签。完整触发场景见 `rules/commercialization.md` 第 6 节。

**原则 6｜扩展方向对标 🟡 建议级** — 设计玩法 / 商业化 / 社交 / 数据类新功能时，**建议**做行业对标
（每方向 ≥5 条 S/A 级来源）而非只看通用玩法；**不做对标也可以推进**，但方案中须说明关键设计取舍的依据
（经验 / 对标 / 既有约定）。对标主题、硬性指标、来源权威等级表与 6 步对标流程见 `rules/industry-benchmark.md`。

**方案必须是可长期维护的成熟方案，禁止分阶段 / 渐进式交付** — 方案应一次性完整覆盖所有影响点
（含 UI、存储、测试、旧数据兼容），不允许遗留"后续优化"。方案本身即最终态，执行者照单实施即可，
不应需要自行补充或二次设计。

> **边界说明（防止与本仓库的批次化实施混淆）**：本禁令约束的是**单个方案的完备性**——不得把一个方案
> 拆成"先做一半、剩下的以后再说"。它**不禁止**按批次编排的工程实施：`docs/parallel-batches*/` 系列与
> `docs/cpp-migration-implementation-plan.md` 的"分阶段交付，每阶段有独立验收标准"，是**多个各自完备的
> 方案**的有序执行，每一批本身仍是完整方案。判断口径：若某个"阶段"单独拿出时方案是残缺的（缺影响范围
> 清单、缺兼容性分析、缺盲区自查），那它就不是合法的一批，而是被违规拆分的半个方案。

**最优方案不计成本且需跨 iOS 平台** — 不考虑时间成本、人力成本、计算成本等任何实施成本，要求**全量采纳**
同类型热门游戏（原神、星铁、米哈游系、网易系、腾讯系、莉莉丝、鹰角、叠纸等）的先进设计。若因产品定位、
技术栈限制等客观原因无法全量使用，必须逐条说明无法采纳的原因和替代方案。
所有设计方案（UI 组件、渲染管线、手势系统、存储格式、网络协议等）必须确保 Android 与 iOS 两套平台均可落地，
优先选择跨平台一致的方案；若技术方案依赖 Android 独占 API 或平台特定特性，须在方案中给出 iOS 侧的对等实现方案。

## 一、未来场景推演（防"只看眼前"）🔴 必做

方案必须包含 **"未来场景推演"小节**，至少覆盖 6 个月档（1 年/3 年档按方案规模选做）：

| 推演维度 | 必答问题 | 反例（历史教训） |
|---------|---------|----------------|
| 规模增长 | 同类内容 ×10 时，本方案成本是否仍然线性可控？（新增 1 个 vs 新增 10 个） | UID 排序分配：新增资源使既有 UID 漂移（2026-08-13 修复为持久映射追加式） |
| 生命周期 | 本方案产出的东西在"构建/重启/重建/清缓存"全生命周期内行为一致吗？ | codegen 的 generatedAt 时间戳进 hash → 增量跳过永久失效（2026-08-13 修复） |
| 平台扩张 | 未来 iOS 端时本方案是否需要重做？（对照 platform-abilities.md 接口缺口清单） | AudioEngine 破坏 core/engine 零 Android 依赖自我声明（audio-thread-audit A1） |
| 运营演进 | 6 个月内数值/配置/活动调整时，本方案是否需要发版？（对照 RemoteConfig 绑定状态） | 数值硬编码 → 每次平衡调整等发版审核 |
| 兼容回退 | 本方案上线后若发现缺陷，能否关闭开关/回退，还是必须再发版？ | 无开关的深度重构 = 一次性赌注 |

## 二、技术债显性化（防"只修眼前、债留身后"）🔴 必做

方案必须包含 **"技术债与偿还计划"小节**，三列表：

| 债项 | 产生原因（为何现在不全做） | 偿还时机（明确触发条件） |
|------|--------------------------|------------------------|
| 例：命令通道零消费者 | 计划批准但无生产消费场景 | 出现纹理流送/动态图集时实现，或下次清理移除 |

**规则：**
- "后续优化"、"视情况而定"不是偿还时机——必须有可判断的触发条件
- 方案完成后，债项同步登记到 `docs/architecture.md` 待办登记表（D 系列）或 `docs/platform-abilities.md` 缺口清单（G 系列）
- 借债默认不允许；确需借债的必须有上述表格

## 三、YAGNI 反向检查（防"为未来臆造"）🔴 必做

- 方案中每个新抽象/新接口/新类型，**必须至少有一个当前生产消费者**（测试不是消费者）
- 无当前消费者的 → 从方案中移除，改登记为二、技术债条目
- 反例：FrameDrawCommand 三命令类（53 行死代码，2026-08-13 删除）；命令 FIFO 通道（实现后对抗审查删除，教训：**计划批准 ≠ 免于 YAGNI 审查**）

## 四、测试成本核算（防"测试拖垮 CI"）🔴 必做

| 检查项 | 必答问题 |
|--------|---------|
| 墙钟成本 | 每个新测试的**真实墙钟时间**是多少？（runTest 虚拟时间 ≠ 墙钟；迭代数 × 单次成本要估算） |
| 上限约束 | 单测试 > 30 秒墙钟吗？（是 → 拆小或降迭代；全量测试预算 ~10 分钟内） |
| 确定性偏差 | 守卫类测试的迭代数是否必要？（确定性偏差是系统性差异，单次迭代即可捕获——100 与 1000 守卫强度相同，见 HeavenlyTrialAnimationGuardTest 修正） |
| 环境依赖 | 测试依赖本机路径/文件存在/构建产物吗？（生成物依赖必须挂 Gradle 任务依赖，见 codegen 守卫测试接线） |

## 五、全局影响交叉核对（防"只见自己模块"）🟡 必做

- 逐项列出本方案触碰的 `rules/*.md` 规范文件（如 economy-design / commercialization / expansion-playbook）并确认无冲突
- 涉及货币/奖励 → 对照 `docs/knowledge-base.md` 经济基线表（源与汇闭环）
- 涉及平台能力 → 对照 `docs/platform-abilities.md`（接口缺口清单 G 系列）
- 涉及存档/Entity → 对照 `rules/database-migration.md`（先读规则再动 Entity）
- 涉及渲染特性 → 对照 `android/docs/renderer-feature-checklist.md`（双端一致性）

## 六、决策分级（防"该小修时大改、该大改时小修"）🟡 必做

方案开头必须声明本方案属于哪一级：

| 级别 | 判定 | 要求 |
|------|------|------|
| **眼前修复**（外科手术式） | 缺陷清晰、根因单一、无扩展需求 | 只改必须改的；引用 Karpathy 准则 3 |
| **架构级重构** | 同模式问题 ≥3 处 / 触及未来 6 个月规划 / 影响跨平台路径 | 按设计方案规则全流程（完整方案文档 + 对抗性审查；行业对标为 🟡 建议项，非强制前置） |
| **中间地带** | 拿不准时 | 按架构级出方案，但明确标注"最小切入路径"备选 |

## 七、盲区自查与完善建议（防"当局者迷"）🔴 必做

方案必须以 **"盲区自查与完善建议"** 作为**最后一个章节**：作者切换到审查者/对抗者立场，系统回答"本方案没有考虑到什么、遗漏了什么"，并逐条给出完善建议。

自查维度（逐项过一遍，禁止只挑容易的回答）：

| 维度 | 必答问题 |
|------|---------|
| 需求理解 | 需求是否存在第二种合理解读？字面需求与用户真实意图是否有偏差？ |
| 边界与极端 | 空值/极值/并发/中断/时序错乱下，本方案是否有定义的行为？ |
| 系统耦合 | 与既有机制的交互（结算层级/EventBus/存档/引导/配置开关/RNG 分区）是否全部枚举？ |
| 假设有效性 | 方案依赖的前提假设逐条列出：如何验证？不成立时的备选路径？ |
| 数据与兼容 | 旧存档/旧配置/中断后的半完成状态下行为是否明确？回滚路径是否存在？ |
| 非功能属性 | 性能/内存/功耗/安全/隐私合规是被评估过，还是默认"不适用"？ |
| 生命周期 | 运营调整、规模增长、iOS 移植时方案是否仍然成立（对照第一节逐项复核）？ |
| 流程盲区 | 测试覆盖不到的部分、监控盲区、发布/回滚流程的薄弱环节？ |

条目三要素：**盲点描述 + 潜在影响 + 完善建议**（建议必须可执行，禁止"加强关注"式空话）。

处置规则：
- 完善建议若实质影响方案主体（补充影响点/新增兼容措施/改变选型），**必须回写方案正文对应章节**，本章节只保留条目索引——禁止把已知缺陷留在附录不处理
- 有价值但暂不采纳的建议须说明理由；构成技术债的同步登记到第二节债表
- 确无实质性盲区时，禁止一句"无遗漏"敷衍——须逐维度给出自查结论与依据

## 八、方案完成度自检（提交用户前逐项勾选）

- [ ] 未来场景推演小节已写（≥6 个月档）
- [ ] 技术债与偿还计划小节已写（无债也需声明"本方案无新增债"）
- [ ] 盲区自查与完善建议小节已写（方案末章，逐条含"盲点+影响+建议"三要素，实质性问题已回写正文）
- [ ] 每个新抽象有当前生产消费者（或已移入债表）
- [ ] 新测试墙钟成本已核算
- [ ] rules/ 交叉核对完成（列出触碰的规范文件）
- [ ] 决策分级已声明
- [ ] 影响范围清单含经济/iOS 标签项（rules/design-plan-review.md第 3 条）
