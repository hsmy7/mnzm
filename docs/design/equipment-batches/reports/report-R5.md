> 变更范围：**仅 C++ bench 测试文件**（`android/app/src/main/cpp/gamecore/test/bench/accrual_segment_bench_test.cpp`），零生产逻辑、零 Kotlin、零 Room、零存档影响

## 1. 做了什么

### 1.1 口径改造（绝对值 → 同机归一化比值）

| 项 | 改造前 | 改造后 |
|---|---|---|
| best 判据 | `best < 1000us`（绝对墙钟） | **`best / calib < 1.55`**（同机比值） |
| P50 判据 | `p50 < 1000us`（绝对墙钟） | **`p50 / calib < 1.90`**（同机比值） |
| 参考负载 | 无 | **遍历 1 MiB 数组的访存型负载**（`kCalibrationArrayBytes` / `kCalibrationPasses = 21`），单次约 647us |
| 采样方式 | 先测被测段（分段） | **交错采样**：每轮先测被测段、再测参考负载，二者经历同一负载窗口 |
| 绝对耗时 | 作判据 | **降级为打印观察项**（best/p50/max/遥测 overBudget 全部保留打印） |

**预算定标依据**：参考负载单次耗时调到与本机安静窗口积分段同量级（646–647us vs 632–638us）⇒ 安静比值 ≈ 1.0。best 预算取**原 1ms 绝对预算的等效比值**（1000 / 650 ≈ 1.54，取 **1.55**），即**与原口径同严格度**，但对机器快慢免疫。

**生产常量未动**：`GameCore::kAccrualSegmentBudgetUs = 1000` 仍驱动 `game_core.cpp:409` 的遥测超预算计数，语义不变。

### 1.2 两处根因修复（过程中实测发现，非预期改动）

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 参考负载耗时恒为 **0** | 定长乘加链无副作用，编译器**整段常量折叠**；`static_cast<void>` 挡不住 | 结果写入 **`volatile double gCalibrationSink`**（易失写入是真实内存屏障） |
| 2 | 分段测量会歪曲比值 | 先测被测段、后测参考负载 ⇒ 负载只落在其中一段时比值失真 | 改为**每轮交错**采样（同一负载窗口） |

| 2 | 632.3us | 644.6us | 647.0us | 0.977 | 0.996 | OK |
| 3 | 636.0us | 696.7us | 648.5us | 0.981 | 1.074 | OK |
| 4 | 637.4us | 845.8us | 647.1us | 0.985 | 1.307 | OK |

### 2.2 全量门禁

| 门禁 | 结果 |
|---|---|
| `cmake --build .`（gamecore desktop-test） | ✅ 成功（无 error） |
| **`ctest` 全量（亲跑）** | ✅ **1532/1532，100% passed，0 failed**（56.56s） |
| three bench cases 单跑 | ✅ `SegmentUnderBudgetAt5000` / `SegmentFullInventoryObservation` / `SegmentSmallSectWellUnderBudget` **3/3 PASSED** |

### 2.3 🔴 边界实测（**负结果，必读**）

**(1) 超量调度下归一化判据仍会红** —— 制造 16 路 CPU 竞争（超过物理核数）：

| run | best | calib | ratio best | ratio p50 | 判定 |
|---|---|---|---|---|---|
| 1 | 1183.5us | 667.2us | **1.774** | 1.814 | 红 |
| 2 | 1200.6us | 665.0us | **1.805** | 1.945 | 红 |
| 3 | 1182.6us | 665.4us | **1.777** | 2.455 | 红 |
| 4 | 1207.2us | 663.6us | **1.819** | 1.906 | 红 |

⇒ 被测段 **+87%**，参考负载仅 **+3%** ⇒ 比值照涨。**原因（已定位）**：被测 `accrue` 是访存密集路径（5000 弟子对象图、指针追逐、分散访问），对缓存/带宽竞争敏感；任何**合成参考负载**的资源混合都与之不同，涨幅不同步。

**(2) 改参考负载类型也救不回来** —— 先试 ALU 型参考（定长浮点乘加链，938us）：饱和竞争下比值 **1.14–1.17 红**（参考负载恒定 940us）；换成访存型（1 MiB 数组）后仍是 **1.77–1.82 红**。两种代理都失败。

**(3) `std::clock()` 不能用作「被抢占」检测** —— 本工具链（llvm-mingw / UCRT）`std::clock()` **返回墙钟时间**：安静与 16 路竞争下 cpu/wall 均为 **1.000**（实测）。故该探测手段不可用。

**结论**：**纯 (b) 只能消除「机器快慢差异」与「中度背景负载」，无法免疫超量调度下的缓存竞争。** 这与实施文档 §1 我最初"推荐 (a)+(b) 组合"的判断一致 —— 现已被实测证实。

## 7. 追加实施 (a)：串行化 + 安静窗口

> 用户追加指令：**追加 a** —— 把 bench 与构建/其它测试串行化，只在安静窗口执行。

### 7.1 三层改动

| 层 | 文件 | 机制 |
|---|---|---|
| **CMake** | `gamecore/test/bench/CMakeLists.txt` | `gtest_discover_tests(game-core-bench PROPERTIES RUN_SERIAL TRUE RESOURCE_LOCK gamecore_bench)` ⇒ 无论 `ctest -j` 取何值，bench 都不与其它用例并行重叠；三个 bench 翻译单元之间也共用一把锁互斥 |
| **CI** | `.github/workflows/ci.yml` | 测试拆两步：`Run GTest (non-bench)`（`-E 'Bench\.'`）+ `Run bench (wall-clock, serial)`（`-R 'Bench\.'`）；步骤注释显式写明"勿加 `-j`"与方法论缘由（bench 取真实耗时，并行会假红） |
| **本地** | **新增** `scripts/run-gamecore-bench-quiet.ps1` | 把"安静窗口"从口头纪律变成**可执行入口**：前置拒绝并发构建/测试进程（exit 2）/ 构建目录缺失（exit 3）/ 整机 CPU 利用率 > 阈值（exit 4，默认 20%）/ 无 ctest（exit 5）；并自动注入 llvm-mingw 运行库 PATH |

### 7.2 验证（实跑原数字）

| 项 | 结果 |
|---|---|
| **属性生效** | 生成的 `game-core-bench[1]_tests.cmake` 中 9 条 `set_tests_properties` **均含** `RUN_SERIAL TRUE RESOURCE_LOCK gamecore_bench`；`ctest --show-only=json-v1` 复核 RUN_SERIAL / RESOURCE_LOCK **各 9 次** |
| **过滤拆分不漏测** | `ctest -N` = **1532**；`-R 'Bench\.'` = **13**；`-E 'Bench\.'` = **1519**（13 + 1519 = 1532 ✓） |
| **全量回归** | `ctest` **1532/1532 全绿**（50.97s） |
| **CI YAML 语法** | `yaml.safe_load` 解析通过（**5 jobs**） |
| **脚本·正常路径** | 注入工具链 + 安静窗口（实测 CPU 9.3%）→ **13/13 通过，退出 0**（17.26s） |
| **脚本·拒绝路径** | 8 路负载下实测 CPU 55.3% → **拒绝运行，退出 4** |

### 7.3 过程中修的两个自身缺陷（实测发现，非预期改动）

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 脚本调 ctest 报 `术语 'C' 不会被识别` | `$candidates[0]` 在"只有一个候选"时索引到**字符串首字符**（PowerShell 标量/数组陷阱） | `@()` 包裹 + `Count` 判断 |
| 2 | ctest 直跑 bench 全部 `0xc0000135` | 缺 llvm-mingw 运行库 DLL（仓库历史上记过此坑：`ctest` 缺 llvm-mingw bin → 全 `0xc0000135` 假失败） | 脚本按 `build-desktop-jni.ps1` 同约定探测并**注入工具链 PATH** |

### 7.4 边界（诚实登记）

| # | 项 | 说明 |
|---|---|---|
| 1 | 属性只覆盖 **9** 个用例 | 另有 4 个名字含 Bench 的用例（`DiscipleStoreBench.CoreBatchPerPhase`、`DirtyTrackerBench.*` ×3）在**主测试目标**里，未加属性。**经核实它们只打印不断言耗时**（全部 `std::printf`，无 `EXPECT_*` 时间断言）⇒ 竞争不会造成假红，**无需**保护；CI 拆步时随 bench 步一起跑（归组） |
| 2 | (a) 与 (b) 分工 | **(a) 解决执行环境、(b) 解决判据口径**。叠加后：安静窗口内门禁严格（等效原 1ms）、正常 CI 不受机器差异与中度负载影响；超量调度下 (b) 仍可能红——此时靠 (a) 的纪律/脚本保证**不在过载环境取数** |
| 3 | 阈值 20% 未经跨机调参 | 本机安静基线约 3–10%、负载态 55%+，20% 有明显分离度；如目标 CI 机器基线偏高，用 `-MaxLoadPercent` 覆盖 |
| 4 | 本地脚本为**约定入口**而非强制 | 直接 `ctest` 仍可绕过；`RUN_SERIAL` 属性是其中不可绕过的一层（对 `-j` 生效） |
