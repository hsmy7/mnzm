## 发现 —— `PatrolBattleSystem` 月度巡逻轮的结果写回被入口过期快照覆盖

### 现象（玩家可见）

1. **巡逻楼打赢妖兽后灵石奖励丢失**：战斗结果弹窗正常弹出并显示"获得 N 灵石"
   （奖励卡片口径），但玩家仓库 `gameData.spiritStones` 实际**分文未入账**——
   显示与实际不符，玩家实际所得恒少于弹窗宣称。
2. **巡逻冲突战（巡逻队 vs AI 宗门争抢同一妖兽）的 AI 直攻目标移除丢失**：
   遭遇战打完后 `aiSectBeastDirectTargets` 中该目标记录仍在。
3. **巡逻冲突战 Phase 1 的 AI 阵亡写回丢失**：PvP 中战死的 AI 弟子"复活"
   （`aiSectDisciples` 阵亡标记被冲掉）。

### 根因（因果链，逐行可复核）

`PatrolBattleSystem.executePatrolRound`（`PatrolBattleSystem.kt:123`）的编排方式：

1. **入口拍快照**——`:124` `val gd = state.gameData` 把当月账本抄一份（记作 A），
   此后 `gd` 全程不再更新。
2. **战斗过程中三处代码向"真账本" `state.gameData`（事务缓冲）直写**：
   - 冲突分支目标移除：`:168`（写 A + 目标移除）；
   - 冲突战 Phase 1 AI 阵亡：`markAiDeaths` `:774`；
   - 巡逻胜利灵石入账：`applySpiritStoneReward` `:649`（在 `applyVictoryRewards`
     `:537` 内调用）。
3. **胜利结算链从过期快照出发**——`applyResults`（`:403`）内 `var updatedGd = gd`
   （`:410`，链头 = A），胜利时 `updatedGd = applyVictoryGdChanges(result, updatedGd)`
   （`:429`）在 **A** 上补"击败标记 + 引导计数"。链上**不含**第 2 步的三笔直写。
4. **收尾整体覆盖**——`finalizeBattleOutcome`（`:488`）最终执行
   `state.gameData = finalGd`（`:514`），用"A + 击败 + 引导计数"把真账本整个换掉
   ⇒ 第 2 步三笔直写**全部丢失**。

比喻：会计先复印一份月初账本，出纳随后在原件上记三笔进账，最后会计拿自己那份
复印件（补了两个批注）把原件替换掉——出纳记的三笔消失。

### 幸存面（说明覆盖非无差别）

| 结果项 | 是否幸存 | 原因 |
|---|---|---|
| 妖兽击败标记 / 引导计数 | ✅ | 本就在快照链（updatedGd）上 |
| 弟子 HP 写回 / 阵亡标记 | ✅ | 走 `discipleTables.replaceAll` 独立通道，不经 `gameData` 覆盖 |
| 妖兽材料奖励 | ✅ | 经 `InventorySystem.addMaterial` 写实体仓，不经 `gameData` |
| 战报 / 结果弹窗 | ✅ | 战报在 `state.battleLogs`、弹窗在系统内存队列，均非 `gameData` |
| **灵石入账 / 冲突目标移除 / AI 阵亡** | ❌ | 三者均为 `state.gameData` 直写，被 `:514` 覆盖 |

### 证据（守卫测试首版两条失败实锤，非推测）

B05 守卫测试 `ExplorationPatrolRouteTest` 第一版按**代码意图**断言，两条失败：

- 巡逻 PvE 胜利：断言 `spiritStones == 1100`（1000 基础 + 100 奖励）→ 实测
  **1000**（`AssertionError: 灵石奖励必须入账 expected:<1100> but was:<1000>`）；
  同测试中奖励卡片断言通过 ⇒ 弹窗显示与账面不一致实锤。
- 冲突战：断言 `aiSectBeastDirectTargets.isEmpty()` → 实测**未移除**
  （`AssertionError: 冲突目标必须移除`）；AI 阵亡写回与目标移除同根同源。

定线后逐行追溯至 `:514` 覆盖点。守卫测试终版断言已收敛至**当前基线行为**
（仅守护"回退臂无障碍完成生产"的路由契约），缺陷原样保留、不在测试中固化错误预期。

### 为什么既有测试长期未暴露

既有 `PatrolBattleSystemTest` 全部为 "no crash" 冒烟断言（执行一遍不抛异常即过），
从不断言灵石数量、目标清理或 AI 阵亡——三处均为**静默丢失**：不崩溃、不中断流程、
游戏不报错，只有对账才能现形。

### 妖兽防守路径不受影响（对照组）

`ExplorationService` 妖兽防守生产（排期自动防守/迎战）对 `gameData` 的写入
（`appendPendingBeastDefenseResult` → `finalizeBeastDisciples`）是**同一事务内顺序
直写**，无"入口快照链"结构，不存在覆盖问题——守卫测试防守用例（含弹窗/奖励/HP
写回断言）首轮即绿可证。缺陷为 `PatrolBattleSystem` 单点结构问题。

### 为什么 B05 未修（红线约束）

B05 为迁移批，红线"只切生产通道，不改行为：探索/巡逻结果（产出物/数量）逐位一致"。
修复 = 灵石开始入账 = **玩家可见行为变化**，须走拍板流程，不得混入迁移提交。
守卫测试与文档三件套均已按"记录现状"口径落地。

### 影响评估

- **①灵石丢失**：确定性玩家损失，每次巡逻胜利必现（金额 = `BattleSystemResult
  .rewards["spiritStones"]`，妖兽战胜利奖励段）。
- **②③冲突战两项**：函数域内的丢失已实锤；**下游连锁**——当月后段子事件 9
  （AI 兽战余量，`processRemainingTargets`）会把未被移除的目标当作"巡逻楼未处理"
  而**再次派 AI 进攻同一妖兽**，且 Phase 1 战死的 AI 弟子因阵亡被冲掉而再次参战
  （同月二次战斗 + 复活参战）。该连锁成立的**前提是执行时序为"巡逻轮 → 子事件 9"**，
  修复批实施时须先核实月结编排时序（C++ 侧子事件 9 月末全清 `aiSectBeastDirectTargets`
  可能部分掩盖），按核实结果定影响等级。

### 修复方向（供拍板；简单问题，非架构级）

`applyResults`（含 `finalizeBattleOutcome`）弃用入口快照 `gd` 作链头，改为始终以
`state.gameData` **当前值**派生（`applyVictoryGdChanges` / `finalizeBattleOutcome`
的入参改为现值），三笔直写自然保住。改动面约十余行 + 守卫测试恢复三条意图断言
（灵石入账/目标移除/AI 阵亡），一次修复即根因修复（无需特判分支）。
需拍板事项：**是否修复**（修复后玩家开始真正收到巡逻灵石，属正向行为变化）；
若修，② 的时序核实一并纳入该批。
