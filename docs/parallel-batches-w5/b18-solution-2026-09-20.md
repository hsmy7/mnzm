## 2. 臂 γ（G5）判归建议 —— 三个语义问题的答案

### 2.1 γ-1：native 战斗 `error` 信封的用户可见语义

**答案：维持现状 = 引擎内部容错信号，玩家无感。** `out.containsKey("error")` → null → 调用方 Kotlin 重执行 → 战斗照常出结果。这不是"静默吞掉"（战斗没有丢失，只是引擎降级），也**不应**改成抛业务异常/战斗失败 UI——那会引入新的失败面与 UI 工作，产品上更差。守卫面由 KDoc 契约 + 桌面 `Diff*` 对拍承担（JVM 无桥，error 分支不可单测，诚实登记勿造假用例）。

### 2.2 γ-2：`!GameCoreBridge.isLoaded` 时战斗如何降级 / 产线是否允许无 native

**答案：产线架构上不允许无 native 运行。** 证据（`NativeEngineFlag.kt` KDoc 自述）：tick 结算**恒走 native（无 Kotlin 路径）**，native 不可用 → 该旬跳过结算 → 看门狗 → 紧急重启自愈。即 `.so` 加载失败的设备**游戏整体本就不可运行**，战斗兜底救不了它。因此 Kotlin 战斗实现的真实价值是：

1. **error 信封容错**（native 战斗内容级失败时 Kotlin 仍能出结果——真正保留理由）；
2. **JVM 测试回退面**（全部 JVM 单测靠 `isLoaded=false` 走 Kotlin，如 `EncounterBattleServiceRouteTest`、`RoadFacadeImplTest`、各 `*NativeTxGateTest`）；
3. **`Diff*` 五套的活体对照面**（对拍需要两边都在库里）。

### 2.3 γ-3：是否删 Kotlin `BattleSystem`

**答案：不删。** 321 行（非 3.5 万行），一身三职（§2.2 的 1/2/3），删除收益≈0、破坏面巨大（`BattleSystemTest` + `Diff*` 五套 + 全部 JVM 回退测试）。
