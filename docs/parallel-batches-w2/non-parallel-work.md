> 这四项都不是"实现工作量"问题，而是"要不要做/接受什么代价"的问题。**未拍板就派工 = 白做**。

### P1. WS-4 NPC 移动系统

| 项 | 内容 |
|---|---|
| 现状 | E3 NPC 纯组件族已就绪（`ecs/npc_component.h`：NpcId/NpcPosition/NpcVelocity/NpcPath/NpcPathIndex/NpcSpriteId/NpcAnimState + 渲染快照通道）；寻路三要素（静态地形 `terrain.h` + 建筑占位 + 道路）已在 C++ 齐备 |
| **缺什么** | **NPC 玩法设计文档**：① 数量上限 ② 生成规则 ③ 与弟子系统的关系 ④ **可行走语义（树/边界是否阻塞、道路是否加速）** |

| 影响面 | 渲染（Vulkan + Canvas 双路径）、ECS、存档协议（NPC 是否入档）、性能（低端机上界） |

### P2. P1-5 月结配对结构级优化

| 项 | 内容 |
|---|---|
| 现状 | 常系数已优化（RNG 引用提升 + 位图判定，每对 O(1)）；**M×F 循环形状 = RNG 消费序**（Kotlin 逐位对拍红线） |
| 决策点 | 是否接受**改变配对行为基线**？结构级降复杂度（如按条件预筛候选集）必然改变 RNG 消费序列 → 双端同步改算法 + 重锚所有既有对拍场景 |
| 若同意 | 双端同步修改 + 新的黄金用例锁定 + 对拍场景全量重跑 |
| 若不同意 | 维持现状（**中等规模存档已达标**，仅大规模存档需优化） |

### P3. 地图跨版本冻结协议

| 项 | 内容 |
|---|---|
| 现状 | 地形不入存档/镜像协议（`terrain.h` 确定性重生 + Kotlin 按种子缓存）——**存档与每旬同步零负担** |
| 决策点 | 是否需要"地图跨版本冻结"语义（即：游戏版本升级后，旧种子的地图**保持不变**）？ |
| 代价 | 入 ProtoBuf + C++ 镜像域：存档 +~30KB、每次 exportState/镜像同步 +~80KB JSON（**WS-1 刚优化掉的持续代价会回来**） |
| 若不需要 | 维持现状（与迁移前 Kotlin 版行为一致：生成器演进会改变旧种子地图） |

### P4. 死代码删除（`TimeSystem.onPhaseTick` / `GameSettingsData.autoSave`）

| 项 | 内容 |
|---|---|
| 现状 | **已拍板保留**（handover §4.2）：前者是 6 个 Diff 测试文件的 Kotlin 跨语言对拍基准；后者是序列化设置字段（删除需改 schema + 迁移） |
| 决策点 | 是否推翻该拍板？ |
| 若推翻（前者的代价） | 需先把 6 个对拍测试改写为纯 C++ 断言——**会失去独立 Kotlin 基准**（防"复刻漂移"的最后一道防线） |
| 建议 | **维持保留**（删除的收益远小于失去基准的风险） |
